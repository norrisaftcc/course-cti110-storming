Speaker notes · Defects · ~1.5 min · running 4.5

Start with fairness: it runs. There is no error. The defects are about meaning, not crashes.

One: the meter is on the screen at every choice, and nothing reads it. Two: the save file is plain text, so a player can type the winning room into it and load. Three: the amulet choice is real one way only; leaving it is the same as never seeing it.

Ask the room: which of these would a user story have caught? All three. A story asks what a thing is for, and how you would check it.

The panels are mock-ups in console form. The case study found the same three kinds of defect in its web page.

What the sand castle did better

  • It played sooner. First playable build about 16 minutes earlier on the agent clock. The two builds ran side by side, so this is not a clean race.
  • It looked richer. Art, animation and a character-builder screen. The blueprint build had no art at all.
  • It carried more of the wishes. More of what the prompts asked for made it into the file.
  • It was longer. 1,626 words of player text, against 809.
  • It did not crash. Every path ended somewhere. No errors.
  • It needed nothing installed. One file. Double-click and play.
Case study listed in cyoa-unit/SOURCES.md (its AUTOPSY.md section 7, "What the sand castle did better")

The blueprint, 2 of 3BLUEPRINT

Three layers. One frozen engine.

Display display_plain.py · display_ansi.py · display_curses.py

Ownshow text, choices and meters look. Reading what the player types.

May notimport engine. Change the state. Decide which choices show.

Engine engine.py

Ownsconditions, effects, dice, moving between scenes, save and load.

May notcall print or input. Hold game text. Know a scene id.

Story stories/story.json

Ownsevery scene, choice, ending, field, meter and flag. All game text.

May nothold code. Hold comments: notes go in your blueprint.
